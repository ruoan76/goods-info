三、P0 严重问题（开发前必须修）

P0-1 权限穿透：录入员能进全部管理后台

现象：顶部角色切换器切到「录入员（张三）」后，左侧"管理后台"5 个菜单（分类与属性模板、条码管理、基础字典、数据治理、用户管理）依然全部可点击并正常打开页面。

证据：CSS 第 112 行 body.admin .nav-item .adm{display:none} 只隐藏了"管理员"文字徽标，没有任何规则隐藏菜单本身；switchRole() 只切换 roleTag 文案与 body class，go() 函数无任何权限判断。权限矩阵（用户管理页）却明确写着录入员对"分类/属性模板/条码/字典"、"用户管理"均为「—」。

影响：原型自称"切换角色体验权限差异"，实际演示的是错误行为；若按此实现，录入员可直接打开用户管理给自己提权，权限体系形同虚设。这是安全级问题，不是体验瑕疵。

建议：① 非管理员视角下整个 .nav-group.admin 用 display:none 隐藏；② go() 增加角色守卫，直接跳转 admin 类菜单时拦截并提示；③ 角色切换器补上第三档「只读」，让权限矩阵三列都可演示。

P0-2 数据保真回潮：啤酒分类路径错误 + 补价计数自相矛盾

现象 A（路径错）：详情页第 371 行、分类页第 492 行写「食品 → 酒类 → 啤酒」，但实库查证 C0203 的 parent 是 C02、path 为 /C02/C0203/，正确路径是「酒类 → 啤酒」。食品(C01)与酒类(C02)是并列大类，啤酒不在食品之下。此错误 v1.1 曾修过，本轮回潮。

现象 B（计数错）：补价清单页 page-desc 显示剩余 53,574 条，但脚本第 904 行 let fpLeft=537。点一次"保存"后计数骤变为 536，与首页概览卡、page-desc 的 53,574 完全对不上。

影响：原型承诺"数据与真实库一致"，这两处直接破坏可信度；开发若照抄路径会污染分类导航，计数 bug 会被当成真实逻辑。

建议：统一改为「酒类 → 啤酒」；fpLeft 初值改为 53574（或改为按页面显示值递减）。

四、P1 重要问题

P1-1 20 处空壳按钮，核心管理动作无表单

机器扫描确认 20 处 onclick="toast(...)"，点击只弹提示。需分级处理：

类别具体按钮评审意见
断头动线商品档案"查询"、治理页"查看积压商品"、治理页"导出清单"查询按钮不真过滤（用户管理页却真筛选，标准不一）；"查看积压商品"理应跳转到商品档案·未分类节点，是明确断头，必须补
核心功能空壳分类页"编辑/设置属性模板"、条码页"提交换码"、字典页"新增单位/编辑"×3、批量导入"上传并校验"、属性页"保存属性"这些是方案二的管理核心。作为可演示原型建议至少补 1-2 个关键表单（属性模板、字典编辑），其余可标注"开发期实现"
原型合理留白导出数据×2、影响分析、外部编码对照、条码检查、导入说明、类目增设提案等属重功能或跨系统动作，原型阶段用 toast 说明可接受，但建议统一加"（原型演示）"前缀避免误解

P1-2 分类管理页的树是"半静态"，与商品档案页不一致

现象：分类管理页（s-category）中生鲜冷品、饮料、家居用品、数码五金等节点的 ▸ 箭头没有 onclick，点不开；只有食品/酒类是硬编码展开的静态 HTML，节点也没有商品档案页那样的完整 149 小类数据。而商品档案页的树有 tg() 折叠、pickCat() 联动、搜索框过滤，是真交互。

建议：两处树应复用同一套渲染函数（buildTree()），分类管理页也做成可展开的完整树，管理员才能维护任一小类的属性模板。

P1-3 业务黑话残留：置信度数字直接暴露

基础字典页"数据来源说明"表格第 560/561 行显示「更可靠（0.90）」「次可靠（0.70）」。0.90/0.70 是系统内部置信度分值，v1.2 评审曾明确要求术语清零，这里回潮。业务人员看到小数分值只会困惑。

建议：去掉括号里的数字，只保留「更可靠 / 次可靠」人话，采用规则用文字说明即可。

P1-4 详情页"点击分类可调整"是空声明

详情页第 352 行 meta 写「分类：啤酒（点击分类可调整）」，但该行文字不可点；真正的分类修改藏在"基本信息"Tab 下方的 select 里，且选项还是错的"食品→酒类→啤酒"（见 P0-2）。建议：要么让 meta 那行可点直接弹分类选择器，要么去掉"可调整"文案，避免误导。

六、通过项（确认无误）

以下 8 项经机器校验 / 实库对账，确认正确：
  1. 数据规模一致：4,325,381 总数出现 3 处、197,059 未分类 5 处、138,083 一码多品 3 处、53,574 待补价 3 处、31,088 啤酒 3 处，跨页面无矛盾（计数 bug 除外）
  2. 分类树数据保真：13 大类 / 149 启用小类及各自商品数与 PG 实库逐条吻合（含卷烟 103 小类）
  3. 扫码残留清除干净：全文件仅剩 2 处说明性文字，无任何扫码功能入口或 scanGo 等函数
  4. 定位对齐方案：首页、建档流程、授权边界均与方案 v3.5 一致，扫码类归附录 B
  5. 用户管理交互闭环：统计卡 / 真筛选 / 详情抽屉 / 表单校验 / 状态与密码管理全部可用，确认框支持回调真落地
  6. 左树右表 + 即点即改：商品档案树可选中联动、字段点字变输入框、回车保存
  7. 两段式查重：条码命中 + 同名命中双路反馈，命中禁止建档，与架构 /api/v1/goods/check 端点对应
  8. 技术校验全过：JS 语法通过、0 个缺失元素 ID、0 个未定义事件函数，文件 67KB 结构完整

七、修订优先级建议

建议分两批落地：
  • 第一批（v1.7，开发启动前必做）：P0-1 权限拦截（含补只读角色）、P0-2 两处数据修正、P1-4 分类声明、P1-3 置信度数字清理。改动量小、风险高，必须清零。
  • 第二批（v1.8，进入开发同期）：P1-1 断头动线（查询真过滤、查看积压跳转）+ 补 1-2 个核心表单（属性模板 / 字典编辑）、P1-2 统一树组件、P2 视觉与提示优化。
总体判断：系统骨架与业务定位已经稳定，剩余问题是"打磨"而非"返工"。P0 修复后即可作为 D1 开发的交互基线。
