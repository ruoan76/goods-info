本方案把已完成评审的设计成果转成可排期、可执行、可验收的开发任务。所有技术参数均取自远程环境与实库实测，不推测。

4. 四条铁律与留痕（D2~D3 地基）

前端原型所有提示文案与后端守卫规则一一对应。铁律测试不全绿，不得进入 D4。

#铁律生效端点单元测试断言
①新增必查重：verdict=BLOCK 直接拒（业务码 3001），verdict=WARN 需人工确认；40.6% 同名多码基数下不自动合并POST /goods/check · POST /goods条码命中/同名命中/别名反向三路均返回正确 verdict；BLOCK 时建档必然失败
②条码建档后不可改；唯一变更通道是 Steward 的 /barcodes/reassignPOST /goods · PATCH /goods/{barcode}PATCH field 白名单不含 barcode；尝试改条码返回 422
③VOIDED 联动写 mdm_barcode_alias 登记 90 天禁复用期，不可逆POST /goods/{barcode}/status转 VOIDED 后别名表新增记录；ACTIVE→VOIDED 合法、VOIDED→ACTIVE 返回 3007
④所有改动留痕：谁、何时、改了什么；审计表 goods_app 无 UPDATE/DELETE 权限全部写端点audit() 生成 MAN 批次号；goods_app 对 sys_change_log 执行 UPDATE 必被拒
三道防线：pydantic schema 校验（类型/枚举/必填） → ironrules service 守卫（业务规则） → DB CHECK 约束（金额非负、等级 A-D、version≥1）。任何一层失败都不得写库。乐观锁 version CAS 冲突返回业务码 3009，前端提示刷新重拉详情。

D1 · 桥接通道 + m1 迁移
交付物：venv 可导入 FastAPI / wheels 全量（以 lock 解析数为准）/ dist 闭环 / m1 已迁移

D2~D3 · FastAPI 骨架 + core 横切
交付物：main 工厂 / db 双连接池 / JWT / audit / ironrules + 铁律单元测试
  1. main.py：FastAPI 工厂 + 全局错误处理器（业务码 200+code / 422 / 500+错误 ID）+ 请求 ID 中间件
  2. core/db.py：goods_app 读写池 + goods_ro 只读池，隔离区 DAO 强制走 ro 池（SQL 层 REVOKE 双保险）
  3. core/auth.py：POST /auth/token OAuth2 Password Flow、PBKDF2 校验、JWT HS256 8h（claim 含 sub/role/ver/exp）、require_role Depends。令牌状态一律落库，禁用内存表（架构 2 worker，内存跨进程不共享）：① 登出 → UPDATE sys_user SET token_version=token_version+1，JWT 的 ver 与库中不一致即拒（旧令牌在全 worker 立即失效）；② 登录失败 → sys_user.failed_attempts+1，达 5 次写 locked_until=now()+10min，成功后清零。令牌状态一律落库、不写内存表、不引 Redis。本节修正架构 v1.1 §安全设计的"令牌黑名单内存表（重启即清）"方案（2 worker 多进程下内存不共享、登出无法跨进程生效），改 token_version 落库，列入回写架构 v1.2 备案清单；架构 6 项裁决本身不变；两逻辑纳入 tests/test_auth_state.py（多 worker 语义用并发请求模拟验证）
  4. core/audit.py：audit() 统一写入，MAN 批次号生成，写 sys_change_log + mdm_goods_history 同事务
  5. services/ironrules.py：4 铁律函数；tests/test_ironrules.py 覆盖全部断言分支

验收：铁律测试全绿；/docs 可访问；goods_app 越权 UPDATE 审计表被 DB 拒绝。

  4. 备份 cron：每日 pg_dump | gzip 到 /data/backups/，保留 7 天；全量灾备恢复演练（DBA 账号建临时库 → 恢复 207M 基线备份 → 计时）。与 D1 的"m1 可撤销验证"目的不同，不重复计

验收：浏览器 :8090 静态页 + API 全链路走通；停 gunicorn 后 systemd 自动拉起；灾备恢复一次通过并记录 RTO。

5.1 前后端并行协调机制

后端 D4~D6 与前端 D7~D10 有时间重叠，必须有明确的契约冻结与联调机制，否则两线各自为政。接口方案 v1.2 的 40 端点契约即唯一真相源。

机制做法责任方
契约冻结D1 把 v1.2 的 40 端点录入 openapi.yaml（或从 FastAPI 代码反向生成），前端据此写死 api/client.js 的方法签名；冻结后变更须走评审后端主责，前端确认
Mock 先行D4 后端端点未就绪时，前端用 api/mock.js 按契约返回假数据（结构必须与真实响应逐字段一致），D7~D10 照常推进前端
逐 Router 联调后端每完成一个 Router（auth→goods→categories→attributes→barcodes→admin），通知前端切换该域从 mock 到真实端点，当天完成该域回归双方
契约一致校验前端 api/client.js 的每个方法与 OpenAPI 路径一一对应；§5.2 映射表的端点一律从 OpenAPI 自动提取，禁止手抄（v1.1 曾因手抄写错 2 处）；D11 联调时机器比对：40 端点全覆盖、0 裸 fetch、0 字段漂移双方
关键提醒：前端原型 v1.8 里 18 个交互函数注释了对应端点路径，接入真实 API 时直接把注释里的路径换成 client.get/post/patch() 调用即可——原型的交互逻辑无需重写，只需替换数据层。
