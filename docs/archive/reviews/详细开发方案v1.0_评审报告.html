一、总体结论

方案质量延续了接口 v1.2 的水平——基于实测、显式处理口径差异、把排期落到可验收，方向与非功能设计都扎实，无方向性错误。但作为"可开工"的执行方案，有 2 个 P0 必须在 D1 前解决：

  • D1 前置自相矛盾：要求"dist 部署后浏览器 :8090 可见"，但把 nginx 站点配置排到了 D11 —— 没有站点配置，D1 的三项前置"全绿"永远无法判定。
  • 安全地基缺陷：登出黑名单与登录失败锁用"内存表"，而架构明确 gunicorn 2 worker，内存状态跨进程不共享 —— 登出在另一个 worker 上失效，是真实的安全漏洞而非瑕疵。
启动判定：暂不具备开工条件。先修 2 个 P0（改动量都很小：nginx 站点配置前移 + 令牌状态落库），再按 P1 补齐排期算术与契约口径，即可进 D1。

二、问题清单

P0-1D1 前置"浏览器 :8090 可见"与 nginx 站点配置排在 D11 时序矛盾

D1 里程碑第 3 条要求"前端最小 Vite 脚手架 → scp dist → 浏览器 :8090 可见（SPA 回退验证）"，D1 验收写"三项前置全绿 → 进入 D2"。但 D11~D12 的第 1 条才写"nginx goods-mdm.conf：root 指 dist、try_files 回退、/api/v1 反代"。

实库/环境实测：nginx 1.18.0 已安装，但 /etc/nginx/sites-enabled/ 仅有 penetration-ip-https，无 goods-mdm 站点；ss -ltnp 查 8090 / 8000 均无监听。也就是说 D1 把 dist 拷过去，没有任何站点指向它，":8090 可见"无法验证。

建议：把 nginx 最小站点配置（root + try_files，先不含反代）提到 D1 第 3 条，D11 只补 /api/v1 反代与 systemd。同步修改 D1 交付物与验收文案，让"三项前置"可实际判定。

P0-2登出黑名单 / 登录失败锁用"内存表"，与架构 2 worker 多进程冲突

D2~D3 第 3 条写"登出黑名单内存表、登录失败 5 次锁 10 分钟"。但架构方案 v1.1 明确部署形态为 gunicorn + UvicornWorker ×2 worker，开发方案 §1 部署图也写"gunicorn + UvicornWorker"。

后果推演：用户在 worker A 登出 → 令牌写入 A 的内存黑名单；下一个请求被分发到 worker B → B 不知道该令牌已登出，请求照常通过。登录失败计数同理，被两个 worker 各记一半，"5 次锁 10 分钟"实际变为约 10 次才触发，且锁只在单个 worker 生效。架构裁决"不引 Redis"不能成为内存态的理由。

建议：令牌状态落库——sys_user 增 token_version INT，登出时 version+1，JWT claim 带 version，端点校验时比对；或登出黑名单写 sys_token_blacklist 表（带过期时间，定时清理）。登录失败计数同样写 DB 或 sys_user.failed_attempts / locked_until 字段。两方案都不引 Redis、不破坏架构裁决，且可被契约测试覆盖。

P1-1端点方法分布写错：POST 16 / PUT·PATCH 6，实测应为 15 / 7

§0 口径差异段写"40 个（GET 18 / POST 16 / PUT·PATCH 6）"。机器扫描接口 v1.2 总览表实测为 GET 18 / POST 15 / PUT·PATCH 7，合计同为 40，但 POST 与 PUT 各差 1。

差异来源：PATCH /goods/{barcode}、PUT/PATCH /goods/{barcode}/attrs 等属 PUT·PATCH 域，方按 6 个漏算了 1 个。方法分布是契约测试的参数，写错会导致测试集按错误方法生成。

建议：改为"GET 18 / POST 15 / PUT·PATCH 7"，并让契约测试直接从 OpenAPI 反推分布，不手填。

P1-2D4~D6 三日拆分算术漏 2 个端点，"goods 剩余 4"应为 6

D4~D6 拆分原文："D4 完成 auth 2 + goods 查询/详情/查重/建档/PATCH（7 个）→ D5 完成 goods 剩余 4 + categories 7 + attributes 3 + barcodes 3 → D6 完成 admin 14"。

核对：接口 v1.2 的 goods 域实测 11 个端点，D4 做掉 5 个（查询/详情/查重/建档/PATCH），应剩 6 个（分类调整/状态流转/属性 GET+PUT/导入/导出），而非 4。按原文加总：D4=7 + D5=17 + D6=14 = 38 个，比 40 少 2 个。Router 总数表（2+11+7+3+3+14=40）是对的，错在三日拆分。

建议：D5 改为"goods 剩余 6 + categories 7 + attributes 3 + barcodes 3 = 19 个"，并为 D5 标注这是三天里最重的一天；或把 goods 的导出/导入挪到 D6 与 admin 分摊。

P1-3"5 张新表"实际列了 6 张 —— sys_role 是否建表口径不一

§3 m1 表格列出：sys_change_log、sys_user + sys_role、sys_unit、sys_attr_template、sys_import_job —— 按表名数是 6 张。但全文 4 处写"5 张目标表 / 5 张新表"，接口 v1.2 也写"新建 sys_user + sys_role"后接"m1 幂等建 5 张新表"。

机器核对接口 v1.2：sys_role 仅出现 1 次、sys_user 2 次，角色在契约里是英文枚举（Viewer/Operator/Steward）而非独立表。开发方案把它写成一张表，与"5 张"冲突。

建议：二选一并写死：① 角色用枚举存 sys_user.role 字段，不建 sys_role 表（保持 5 张，与接口 v1.2 一致）；② 确需 sys_role 表则全文改"6 张"并回写接口 v1.2。推荐 ①。

P1-4"19 项功能覆盖"缺可追溯映射，D13 验收引用不准确

D4~D6 验收写"19 项功能覆盖"，D13 写"方案二 v3.5 §6 验收标准逐条勾验"。核对方案二 v3.5 原文：确有"5 大功能域 · 19 项功能"，但 §6 验收标准原文是"四条铁律系统可验证"，不是 19 项功能。

方案里既没列这 19 项是哪 19 项，也没给"19 项功能 → 40 端点"映射，D13 勾验时无清单可依；且把 §6 的引用对象写错。

建议：加一张"19 项功能 → 端点 → 验收动作"对照表（可直接从方案二 v3.5 功能清单抄），D13 改为"方案二 v3.5 功能清单 19 项 + §6 四条铁律逐条勾验"。

P1-5回滚演练账号未明确，goods_app 实测无 CREATEDB 权限

D1 第 4 条要求"从基线备份恢复到临时库做回滚演练"，D1 验收也写"m1 可回滚"。但 PG goods_mdm 当前业务账号是 goods_app。

实测：goods_app | rolcreatedb=f | public schema CREATE=t | goods_mdm CREATE=t。即可在建表（m1 可行），但不能创建数据库——恢复到"临时库"这一步用 goods_app 必然失败。当前库列表只有 goods_mdm / postgres / template0 / template1。

建议：写明回滚演练用 DBA 账号（如 postgres）createdb goods_mdm_rollback_test 后恢复，goods_app 只做 m1 正向建表；并把这条写进启动检查清单的"数据"栏。

P2-119 个 wheel 的数量需按依赖实际核对

D1 写"17 个 + gunicorn + pyjwt = 19 个"。pip download 会连带下载依赖（gunicorn 依赖 packaging 等），实际 wheel 数很可能超过 19。

建议：改为"以 requirements.lock 全量下载结果为准（预计 ≥19），版本锁定"，不要写死数量作为验收条件。

P2-2恢复演练在三处重复出现，目的未区分

D1"回滚演练一次"（验证 m1 可撤销）、D11~D12"恢复演练一次通过"（验证灾备）、§6 测试策略"恢复演练：基线备份→临时库→m1 重放"（验收标准）三处写了同一动作。

建议：明确两者目的：D1 是 m1 可逆性验证（小临时库、只验建表撤销）；D11 是 灾备 RTO 验证（全量 207M 备份、计时恢复）。§6 合并为一条，分别标注 D1 / D11 通过标准。

P2-38090 / 8000 端口语义需在 D1 站点配置中明确

方案 D11 写 /api/v1 反代到 127.0.0.1:8000（FastAPI），8090 是 nginx 对外端口，这与架构一致。但架构方案另有一处写"nginx 新增站点 /api/v1 反代 :8090"（疑为原文笔误），且 D1 没提前说明 dist 该放哪个 root。

建议：D1 站点配置里把端口语义与 root 路径写死：listen 8090; root .../frontend/dist; location /api/v1/ { proxy_pass http://127.0.0.1:8000; }，消除歧义。

P2-4goods_app 保留 public schema CREATE 权限，最小权限原则未收口

实测 goods_app 对 public schema 和 goods_mdm 库都有 CREATE 权限（m1 建表需要）。但 m1 完成后若保留，业务账号仍可在生产库任意建表。

建议：m1 脚本末尾加 REVOKE CREATE ON SCHEMA public FROM goods_app;，把建表权限收回 DBA；后续 DDL 走变更流程。与已有的"sys_change_log 仅授 INSERT"形成一致的最小权限体系。

三、通过项（10 项）

  • HTML 结构完整：所有标签全配对，无残留异常字符。
  • 阶段全覆盖：D1~D13 每一阶段均单独出现，架构 D 阶段划分被完整继承。
  • Router 总数正确：2+11+7+3+3+14 = 40，与接口 v1.2 的 40 端点对账一致（仅三日拆分错，见 P1-2）。
  • 口径差异显式处理：架构"约 23 端点" vs 接口 40 的差异在 §0 用警示框写明，以 40 为准且不推翻架构裁决——这是防止漏做 17 个端点的关键设计。
  • 三桥方案与架构一致：wheel 桥 / 构建桥 / 源码桥的方向、命令、用途与架构裁决③完全对齐。
  • 6 项架构裁决完整复述，并写明"推翻任一项须走评审"。
  • 四铁律与错误码对应：3001（查重 BLOCK）、3007（状态流转非法）、3009（乐观锁）三码引用与接口 v1.2 定义一致；audit MAN 批次号、goods_app 无审计表 UPDATE/DELETE 均写入验收断言。
  • 权限实测可行：goods_app 可在 public schema 建表（m1 可正向执行），sudo 免密可用（D11 部署可执行），nginx 已安装（D11 少一步安装）。
  • "19 项功能"出处真实：方案二 v3.5 确有"5 大功能域 · 19 项功能"，非编造（仅缺映射与 §6 引用写错，见 P1-4）。
  • 前后端协调机制到位：契约冻结 / Mock 先行 / 逐 Router 联调 / 机器比对四机制完整；"前端 18 函数注释含端点路径、接 API 只换数据层"的洞察准确，可显著减少联调返工。
