一、总体结论

主链路对齐，但存在两处"前端承诺了、后端没有"的能力空洞——这不是字段细节，而是界面上明明白白展示给用户、权限矩阵也打勾、后端 35 个端点里却完全不存在的功能。若直接进 D2~D3 开发，首页会退化成静态演示页，导出按钮永远只能弹提示。

前端 v1.7 · 10 页面→35 端点逐条比对→8 页主链路有支撑→2 页核心内容无端点

好消息是：14 处前端空壳按钮其实后端端点已经现成，只是前端没接——这部分不需要改后端，是纯前端工作量。真正需要后端补的只有 3 类端点（统计概览、变更日志、导出）。

判定：不建议"原样进入开发"。先按本报告补 后端 v1.2（+3 类端点） 与 前端 v1.8（接 14 处现成端点），两边并行、互不阻塞，之后即可作为 D2~D6 的联合基线。

三、问题清单

P0-1　首页统计卡与"最近处理"没有任何后端端点

前端证据：s-home 顶部 4 张卡写死 4,325,381 / 13·149 / 53,574 / 197,059；"最近处理"三条含操作人、前后值、时间（今天 09:12 售价 218→220 等）。
后端证据：35 端点全文扫描 export|dashboard|change-log|activity|stats|summary 关键词 0 命中；sys_change_log 只在写操作里被提到"写"，没有任何读端点。
影响：首页是系统门面，上线后四个数字永远是硬编码快照，业务做一次补价后数字不会动；"最近处理"永远是三条演示数据——用户会立刻判定"这系统没接真实数据"。
建议（后端 v1.2 新增 2 端点）：① GET /admin/dashboard 返回 {goods_total, categories, price_pending, unclassified, todo_counts}，其中业务总量可用 pg_class.reltuples 近似、待办数需精确；② GET /admin/change-log?limit=10 读 sys_change_log 最近变更（含 operator / field / old / new / time），直接喂首页时间轴。

P0-2　"导出数据"三处按钮 + 权限矩阵全打勾，后端无导出端点

前端证据：首页"导出数据"、档案页"导出当前分类的筛选结果"、治理页"导出待处理清单"共 3 处按钮；用户管理权限矩阵明写"导出数据：录入员 ✓ / 管理员 ✓ / 只读 ✓"；20 处 toast 中空壳导出占 3 处。
后端证据：35 端点无 /export 路径，全文 export 关键词 0 命中。
影响：权限矩阵承诺了一个不存在的能力——这是契约层面的自相矛盾，比单纯的按钮空壳更严重：开发照矩阵实现权限会发现无端点可挂，测试照矩阵验收会判定失败。
建议（后端 v1.2）：① GET /goods/export：流式 CSV、复用 GET /goods 全部过滤参数、字段白名单、Viewer 可导出（金额按定点字符串输出）；② GET /admin/quarantine/export：治理清单导出，同样走 goods_ro；③ 前端权限矩阵保持"三角色可导出"不变，无需回退。

P1-1　用户管理字段不对齐：phone 与活动记录

前端：saveUser() 收集 uf-phone（电话）与 uf-dept，详情抽屉渲染 u.logs「最近活动」；phone/ Dept 在前端共 6 处引用。
后端：GET /admin/users 响应示例为 {account,name,role,status,dept,last_login,permission_codes:[]}——无 phone；端点组描述无用户活动日志读取端点。
建议：后端 users 表补 phone 字段并纳入增删改；补 GET /admin/users/{account}/activity 读 sys_change_log 按 operator 过滤；或前端撤掉电话字段与活动区（二选一，不能各留一半）。

P1-2　单位字典"使用商品数"列无数据来源

前端：s-dict 单位表含"使用商品数"列，值取自实库（000007 → 1,694,410 / 000003 → 640,973 / 000001 → 631,888）。
后端：GET /admin/units 描述仅"单位字典列表（22 种编码）"，全文无 goods_count 字段。
建议：GET /admin/units 增 goods_count。注意 432 万表不能实时 COUNT(*)——建议 m1 建单位字典表时维护物化聚合或在 sys_unit 冗余计数字段，导入任务结束时刷新。

P1-3　14 处前端 toast 其实后端端点已现成（前端未接）

机器枚举 20 处 toast，逐条对照后发现以下 14 处后端已有对应端点，纯属前端原型未接：
前端 toast 按钮可直接调用的现成端点
在当前分类内按输入条件查询 / 查看未分类商品GET /goods?q=&category_id=C00
调整影响分析（啤酒 31,088 个商品）POST /categories/{id}/impact
编辑分类信息 / 设置属性模板PUT /categories/{id} + PUT /categories/{id}/template

条码校验 / 提交换码POST /barcodes/validate + POST /barcodes/reassign

下载 CSV 模板 / 导入说明 / 校验进度 / 失败清单POST /goods/import + GET /admin/import-jobs/{id}
建议：列为前端 v1.8 明确清单，不需要动后端。其中"外部编码对照"是评审报告 v1.0 → v1.1 刚补的端点，前端还没跟上，优先接。

P1-4　前端"按条件查询"仍不真过滤（v1.6 评审第二批遗留）

s-goods-list 的查询按钮仍是 onclick="toast('在当前分类内按输入条件查询')"；治理页"查看积压商品"仍是 toast 不跳转。后端 GET /goods 已完整支持 q / category_id / source / grade / status / price_state 全部过滤参数。
建议：随 P1-3 一并接入，这是前端单方工作量；参数名已与后端对齐，无需契约变更。

P2-1　"转治理处理 / 类目增设提案"属方案边界外，需在原型标注

补价页"先确认商品 → 转治理处理"、治理页"类目增设提案"、字典页来源说明的"规则自动采用"均指向数据治理流程。方案二 v3.5 明确治理裁决不在本期。
建议：前端这两个按钮灰化并加提示"跳转治理系统（本期不实现）"，避免开发误判为接口漏做。

P2-2　前端角色切换是纯演示，需在方案写明生产口径

前端 switchRole() 直接切视角 DOM；后端用 JWT claim + Depends(require_role) 强制。设计本身正确（前端守卫只是体验，后端才是防线），但接口方案未写明这一点。
建议：在 v1.2 安全章节补一句"前端角色切换仅原型演示，生产权限一律以 JWT claim 为准，前端传入的 role 字段不采信"。

P2-3　档位命名映射需在文档固定

前端三档：只读 / 录入员 / 管理员；后端三档：Viewer / Operator / Steward。语义一致但字面不同，/admin/users 的请求体 role 字段取值未明示。
建议：接口方案补一张固定映射表：只读=Viewer、录入员=Operator、管理员=Steward，并规定请求体只接受英文枚举。

四、确认通过项（11 项）

  • 主链路覆盖：10 个页面中 8 个核心操作全部有端点，商品详情、新增商品、分类管理、条码管理四个页面完整对齐
  • 两段查重契约：后端 verdict 三态 PASS/WARN/BLOCK 与前端红/黄/绿反馈一一对应，粒度到"同名命中 40.6% 基数不自动合并"
  • 字段即点即改白名单：后端 field 仅允许 goods_name/inprice/outprice/unit_id，与前端可编辑字段完全一致；分类/状态/条码分别走独立端点
  • 分类树数据契约：171 节点 / 162 启用 / 13 大类 / 149 小类 / C00 占位 197,059，前后端同源同数（合计对账 4,325,381）
  • 分类调整弹窗：前端 v1.7 新落的 openCatPicker/saveCatPick ↔ POST /goods/{barcode}/category 对齐
  • 状态流转权限：前端"停用"仅管理员可见 ↔ 后端 /status 为 Steward，口径一致
  • 批量导入闭环：模板 / 500 行每批 / 失败清单 ↔ POST /goods/import + GET /admin/import-jobs/{id}
  • 用户管理闭环：统计卡 / 真查询 / 抽屉 / 新增编辑 / 启停 / 重置密码全部有端点，统计卡由列表聚合的实现约定也写了
  • 一码多品数字：前端 138,083 ↔ 后端 GET /admin/quarantine，PG 实测隔离区 138,083 条全部为 SAME_CODE_DIFF_GOODS，口径完全一致
  • 权限双层防线：前端三档菜单守卫 + 后端 JWT 角色强制，v1.7 修掉的"权限穿透"在接口层再兜一道
  • 铁律前后端一致：条码建档后不可改、VOIDED 联动 90 天禁复用、查重 BLOCK 不可跳过——前端提示文案与后端守卫规则逐条对应
